## 2. 핵심 기능 요구사항
A. 동기화 제어 (Sync On/Off)

사용자는 "서버 동기화" 기능을 직접 켜거나 끌 수 있어야 한다.

Sync OFF: 데이터가 로컬에만 저장되며 외부로 전송되지 않는다.

Sync ON: 로컬 데이터가 서버(Firestore)와 동기화된다.

구현 전략: 별도의 로컬 DB(SwiftData 등)를 두지 않고, Firestore SDK의 네트워크 제어 기능(enableNetwork / disableNetwork)을 활용해 구현 복잡도를 낮춘다.

B. 데이터 저장 및 캐싱

네트워크 상태와 무관하게 데이터 읽기/쓰기도 가능해야 한다.

C. 사용자 시나리오 및 인증 (Auth Flow)

비로그인 유저 (Guest):

앱 설치 즉시 사용 가능해야 하며 데이터 저장이 가능해야 한다.

구현: Firebase '익명 로그인(Anonymous Auth)'을 백그라운드에서 실행하여 처리한다.

로그인 전환 (Guest → User):

비로그인 상태에서 작성한 데이터는 사라지지 않고 로그인한 계정으로 **자동 승계(Merge)**되어야 한다.

구현: 익명 계정에 소셜 계정(Google/Apple)을 '연동(Link)'하는 방식을 사용한다.

로그아웃:

로그아웃 시 보안을 위해 로컬에 저장된 해당 유저의 데이터와 키체인 정보를 모두 삭제한다.

## 3. 시스템 아키텍처 요약
디자인 패턴: MVVM + Repository Pattern

데이터 흐름: View ↔ ViewModel ↔ Repository(Firestore Wrapper)

핵심 로직:

Repository는 Firestore SDK만 바라본다.

SyncManager가 사용자 설정에 따라 Firestore의 네트워크 줄을 잡거나 끊는다.

복잡한 마이그레이션 로직 대신, Firebase Auth의 Link 기능을 통해 사용자 경험(UX)을 매끄럽게 만든다.

이 내용이 작성자가 의도한 바와 정확히 일치한다.

**"Repository와 SyncManager가 서로 모르는데 어떻게 동작이 유기적으로 연결되는가?"**에 대한 의문일 것이다.

결론부터 말하면, Firebase SDK 자체가 '싱글톤(Singleton)'으로 설계되어 앱 전체에서 하나의 인스턴스를 공유하기 때문이다.

마치 우리 집(App)의 **수도꼭지(Repository)**와 **메인 수도 밸브(SyncManager)**의 관계와 같다.

수도꼭지(Repository)는 밸브가 잠겼는지 열렸는지 신경 안 쓰고 그냥 틀면 된다.

밸브(SyncManager)를 잠그면 수도꼭지를 틀어도 물(데이터)이 밖으로 안 나갈 뿐이다. 하지만 밸브를 다시 열면 고여있던 물이 한 번에 나간다.

코드로 보면 아주 명확하다.

## 보충설명

1. SyncManager (메인 밸브 역할)
이 녀석은 데이터를 저장하거나 읽는 기능은 전혀 없다. 오직 Firestore라는 거대한 기계의 전원 스위치만 관리한다.

Swift

import FirebaseFirestore

class SyncManager: ObservableObject {
    // 앱 전체에서 공유되는 Firestore 인스턴스
    private let db = Firestore.firestore()

    // 사용자가 UI에서 이 값을 바꿀 때마다 네트워크를 껐다 킨다.
    @Published var isSyncEnabled: Bool = true {
        didSet {
            toggleNetwork(isEnabled: isSyncEnabled)
        }
    }

    private func toggleNetwork(isEnabled: Bool) {
        if isEnabled {
            // [ON] 온라인 모드: 서버와 연결, 밀린 데이터 업로드/다운로드 시작
            db.enableNetwork { error in
                if let error = error { print("네트워크 연결 실패: \(error)") }
            }
        } else {
            // [OFF] 오프라인 모드: 연결 끊음. 이제부터 모든 작업은 로컬 캐시에서만 일어남
            db.disableNetwork { error in
                if let error = error { print("네트워크 차단 실패: \(error)") }
            }
        }
    }
}
2. NoteRepository (수도꼭지 역할)
이 녀석은 SyncManager가 네트워크를 껐는지 켰는지 전혀 모른다. 그냥 평소처럼 Firestore에 데이터를 던진다.

Swift

import FirebaseFirestore

class NoteRepository {
    // SyncManager가 제어하는 그 'db'와 똑같은 인스턴스를 바라본다.
    private let db = Firestore.firestore()

    func addNote(title: String) {
        // 네트워크가 꺼져있든 켜져있든 코드는 똑같다.
        // 꺼져있으면 -> 로컬 캐시에 저장됨 (성공 콜백도 바로 옴)
        // 켜져있으면 -> 로컬 캐시 저장 + 서버 업로드 시도
        db.collection("notes").addDocument(data: [
            "title": title,
            "createdAt": Date()
        ])
    }

    func fetchNotes() {
        // 네트워크가 꺼져있으면 로컬 캐시된 데이터를 즉시 리턴한다.
        db.collection("notes").getDocuments { snapshot, error in
            // ...
        }
    }
}

3. 작동 원리 (The Magic)
이 두 클래스가 맞물려 돌아가는 시나리오는 다음과 같다.

사용자가 "동기화 끄기" 선택 (SyncManager 동작)

SyncManager가 db.disableNetwork()를 호출한다.

Firestore SDK 내부적으로 서버와의 소켓 연결을 끊어버린다.

사용자가 글 작성 (Repository 동작)

Repository가 db.collection(...).add(...)를 호출한다.

Firestore SDK는 연결이 끊긴 걸 알고 있으므로, 데이터를 **로컬 캐시**에만 저장하고 "저장 완료" 처리를 한다. (사용자는 딜레이 없이 저장이 완료된 것처럼 느낀다.)

이 데이터는 'Pending Write(보류된 쓰기)' 상태로 마킹된다.

사용자가 "동기화 켜기" 선택 (SyncManager 동작)

SyncManager가 db.enableNetwork()를 호출한다.

Firestore SDK가 서버와 다시 연결된다.

연결되자마자 SDK가 내부적으로 'Pending Write' 목록을 확인하고 서버로 싹 업로드한다.

요약
Repository: "나는 그냥 넣으라고 해서 넣었어. 네트워크가 끊겼다고? 난 몰라, SDK가 알아서 하겠지."

SyncManager: "나는 그냥 인터넷 선만 뽑았어. 데이터가 들어오는지 안 들어오는지는 내 알 바 아냐."

Firestore SDK: "주인이 선을 뽑아서(disableNetwork) 일단 내 주머니(캐시)에 넣어뒀고, 선 꼽으면(enableNetwork) 그때 서버로 보낼게."

이 구조 덕분에 Repository 코드 안에 if isOnline { ... } 같은 지저분한 분기 처리를 전혀 할 필요가 없는 것이다.

또 비로그인 사용자는 오프라인모드라 그냥 로컬로만 처리하기에 서버에 부하도 주지 않는다.(단, 어디까지 영구적으로 기록하는지 확인해봐야함)
